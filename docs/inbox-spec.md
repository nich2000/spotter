# Техническое задание на Inbox и матрицу приоритетов Spotter

Дата: 1 октября 2026 года. Статус: проект ТЗ по согласованной концепции.

Inbox — пространство всех актуальных потенциальных дел, а не список на конкретный день. Оно объединяет входящее из внешних источников, собственные записи и задачи, возвращённые на разбор. Внутри раздела есть неразобранное и задачи с приоритетами в матрице Эйзенхауэра. Дневной план — отдельная выборка из общего набора задач.

Образец: [компактный интерактивный Inbox](mockups/inbox.html). [Редактируемый исходник](mockups/inbox.fragment.html) уточнён по результатам проверки. Данные демонстрационные, обновление источников в макете не подключает реальные приложения. В обновлённом образце основные поля открываются модально, меню строки поддерживает прямое завершение и отмену. Встроенный сокращённый редактор не реализует всю согласованную карточку задачи; её обязательная интеграция остаётся частью разработки.

Связанные документы: [рабочий день](workday-spec.md), [общая карточка задачи](task-card-spec.md), [проекты](projects-spec.md), [статистика](statistics-spec.md). Настоящее ТЗ определяет разбор Inbox и завершение вне плана. Компоновка и поведение общего редактора определяются уже подготовленным ТЗ карточки; сокращённый редактор образца Inbox не заменяет этот компонент.

Общий контракт сущностей, связей и открытых решений: [каркас проекта](project-spec.md). Он уточняет межраздельные инварианты; решения с отметкой `proposal` не становятся утверждёнными требованиями.

## 1. Цель и границы

Дать возможность быстро собрать десятки задач, уточнить только нужные, распределить по важности и срочности, выбрать часть в план и закрыть любую выполненную задачу без обязательного планирования или таймера.

Сохранить верхнюю навигацию «Сейчас», «Inbox», «Проекты», «Статистика», «Моё состояние». Основная композиция: слева неразобранное, справа четыре квадранта. Ручной ввод и состояния внешних источников расположены сверху.

Разработка новых внешних интеграций не входит в этот этап проектирования. Для модальной карточки использовать согласованный отдельный макет и его ТЗ. Реализация должна предусматривать расширение источников и общий редактор задачи для всех разделов.

## 2. Входящие данные

### Внешние источники

Использовать существующие сборщики Calendar, Reminders, Mail и Notes. В интерфейсе выводить для каждого источника время последнего успешного обновления, состояние и ошибку при наличии. Успешная пустая выборка отличается от ошибки доступа. Сбой одного источника не блокирует остальные и не удаляет уже принятые задачи.

Автоматически собранная запись является предложением, а не обязательством пользователя. При первичном импорте она появляется в неразобранном с атрибуцией источника и доступным исходным контекстом. Событие календаря не равно задаче подготовки к нему: производное действие должно явно обозначаться как предложение и оставаться редактируемым.

Принятие предложения происходит при явном действии пользователя: сохранении как задачи, назначении приоритета, добавлении в план или непосредственном завершении. Исходное приложение при этом не изменяется. Не обещать синхронизацию завершения, редактирования или удаления обратно в Apple-приложения.

Повторное обновление не должно создавать дубли уже принятых, пропущенных и завершённых записей с тем же ключом источника. Сохранить атрибуцию и ключ дедупликации после перемещений и завершения. Изменения исходника не должны молча перезаписывать пользовательский текст, приоритет или состояние.

Текущие ограничения источников сохраняются: почта ограничена непрочитанными и размером выборки, заметки — выбранной папкой, календарь — окном сбора. Формулировка «все задачи» означает общий пул собранного пользователем и интеграциями, а не гарантированное чтение всех данных всех приложений. Для источников без устойчивого ID изменения заголовка могут влиять на дедупликацию; это ограничение не скрывать.

Ключ дедупликации включает источник, учётную запись/календарь/список при наличии и устойчивый идентификатор записи. Для повторяющегося события календаря различать конкретные экземпляры: новый срок события не является дублем предыдущего. Для нескольких предложений из одной записи дополнительно нужен устойчивый идентификатор производного действия; при его отсутствии не создавать несколько автоматически принимаемых задач из одного ключа. Изменение или исчезновение исходника не является автоматическим завершением либо удалением локальной задачи.

Действие «Пропустить» скрывает предложение с возможностью вернуть его. Оно не означает выполнение и не увеличивает статистику. Автоматическое обновление не восстанавливает пропущенное предложение.

### Собственные записи

Строка быстрого ввода принимает название задачи, идею или заметку. Для сохранения достаточно непустого текста. Проект, оценка, срок и приоритет необязательны. Новая запись попадает в неразобранное с источником «Моя запись».

Не требовать немедленного превращения каждой идеи в подробную задачу. При уточнении пользователь может переформулировать текст как конкретное действие и сохранить исходный контекст в описании.

### Возврат из плана и расписания

Незавершённое из закрытого плана получает признак «Требует повторного разбора», сохраняя приоритет, состояние, подзадачи, ожидание/фон, проект и заметки. Такая задача временно отображается в неразобранном с отметкой «Из предыдущего плана»; после подтверждения возвращается в прежний или выбранный квадрант. Не обнулять приоритет ради попадания в список разбора.

Регулярные и назначенные задачи автоматически поступают в Inbox по правилам ТЗ рабочего дня. Одно правило повторения не создаёт несколько незавершённых выполнений. Возврат, повторное обновление и расписание не создают новые копии одной и той же задачи.

Добавление записи из дерева проектов использует тот же путь создания: выбранная ветка задаёт только projectId; при отсутствии выделения задача создаётся без проекта. В обоих случаях она появляется в неразобранном. Приоритет, проект, состояние работы и членство в плане независимы.

## 3. Неразобранное и матрица

Для новой задачи без установленной важности или срочности место по умолчанию — «Неразобранное». Обе оси имеют значения «не определено», «да», «нет». Значение «не определено» нельзя трактовать как «нет».

Матрица состоит из четырёх квадрантов:

| Важность | Срочность | Назначение |
|---|---|---|
| Да | Да | Рассмотреть в первую очередь |
| Да | Нет | Запланировать и защитить время |
| Нет | Да | Передать или выделить ограниченное время |
| Нет | Нет | Отложить либо осознанно отказаться |

Перенос в квадрант устанавливает обе оси и завершает текущий разбор. Перемещение между квадрантами меняет приоритет той же задачи. Возврат на повторный разбор сохраняет существующие значения и требует явного решения для их очистки.

Важность — вклад в выбранную цель или предотвращение существенного ущерба. Срочность — ограничение по сроку и последствия задержки. Не переводить задачи в срочные только из-за возраста записи или числа напоминаний. Автоматическая рекомендация допустима, автоматическое изменение пользовательского приоритета — нет.

Активная задача отображается либо в неразобранном, либо в одном квадранте, но не одновременно в обоих. Завершённое по умолчанию скрыто из активного Inbox и матрицы, но доступно в истории.

## 4. Компактная строка

Одна задача занимает одну строку как в неразобранном, так и в матрице. Предлагаемая высота на компьютере — 32–36 px; на сенсорном экране обеспечить цель нажатия не менее 44 px. Не увеличивать высоту каждой строки ради постоянного вывода проекта, описания, всех тегов и действий.

Состав строки: компактная отметка источника, название, необязательная короткая оценка времени, отметка включения в план и кнопка «⋯». Название занимает оставшееся пространство. Длинное название сокращается визуально, полное доступно в карточке и вспомогательной подсказке при фокусе/наведении. Распознавание источника не должно зависеть только от неоднозначной буквы или цвета; предоставить доступное название.

В Inbox по нажатию на название открывается общая модальная карточка из ТЗ карточки задачи. Это отличается от дерева проектов, где по отдельному пожеланию пользователя требуется двойной клик; не переносить поведение дерева сюда неявно. «⋯» открывает компактное меню действий. Меню и редактор — разные действия; в обновлённом макете это уже показано.

Минимальное меню: изменить приоритет, добавить/убрать из дневного плана, завершить, открыть карточку. Для внешнего предложения добавить «Пропустить». Для завершённого в истории — «Открыть повторно».

Поддержать drag-and-drop между списком и квадрантами. Все действия дублируются меню и доступны с клавиатуры. Перетаскивание не должно открывать карточку случайным кликом. На узком экране колонки перестраиваются без потери содержимого.

Проверить плотность на десятках и сотнях демонстрационных записей. Не ограничивать реальный список четырьмя карточками и не скрывать задачи без счётчика/понятного способа продолжения. Виртуализация или пагинация — технический выбор после проверки объёма; она не должна ломать порядок, доступность и drag-and-drop.

## 5. Модальная карточка задачи

Использовать [согласованный компактный макет карточки](mockups/task-card.html) и [его ТЗ](task-card-spec.md), включая сворачиваемые разделы и общий черновик. Сокращённый модальный редактор демонстрации Inbox показывает только базовые взаимодействия; итоговая реализация использует всю согласованную карточку, а не ограничивается этими полями.

Карточка должна позволять просмотреть и изменить:

- Название и подробное описание/исходный контекст.
- Проект и контекст выполнения: за компьютером, вне компьютера, где угодно.
- Важность, срочность и причину/пояснение при желании.
- Оценку продолжительности, остаток и выделяемое на день время.
- Сложность «простая / средняя / сложная», по умолчанию средняя, по общему контракту карточки и раздела состояния; она не выводится автоматически из длительности.
- Срок выполнения, назначенную дату/время и время появления во входящих как разные поля.
- Повторяемость по общему контракту.
- Подзадачи, прогресс, состояние, причину ожидания/фонового процесса и момент проверки.
- Заметку для возвращения и комментарии.
- Атрибуцию источника и историю существенных действий.

Простая задача не требует заполнения дополнительных полей. Неизвестная продолжительность допустима и не равна нулю. Для длинных задач использовать модель многодневной работы из ТЗ рабочего дня.

Комментарии хранить отдельно от описания с датой создания; не обещать обсуждение с другими пользователями или внешнюю отправку. Правила изменения комментариев и журнал определяются общим ТЗ карточки, без отдельной реализации для Inbox.

Карточка сохраняет несохранённые данные при конфликте версий и показывает причину ошибки. При закрытии с изменениями предложить сохранить или отказаться от них. Обеспечить управление фокусом клавиатуры, доступное название диалога и возвращение фокуса в исходную строку после закрытия.

## 6. Завершение без дневного плана

Задача может быть выполнена из неразобранного или любого квадранта без предварительного выбора приоритета, включения в план, смены на «в процессе» и запуска таймера.

Меню строки выполняет быстрое завершение сразу после необходимых проверок. В модальной карточке завершение сначала меняет черновик и применяется кнопкой сохранения, как установлено ТЗ карточки; отмена закрывает черновик без изменения задачи. Успешно применённое завершение:

1. Сохраняет дату фактической отметки и состояние «Готово».
2. Убирает задачу из активного Inbox/матрицы, сохраняя её в проекте, истории и статистике.
3. Не создаёт задним числом дневной план или фокус-сессию.
4. Сохраняет неизвестную длительность как неизвестную.
5. Предлагает необязательные комментарий, ручную длительность и отметку «Сделано другим человеком».

Если задача находится в текущем фокусе с активным таймером, завершение атомарно останавливает отсчёт, сохраняет фактически учтённое время и снимает фокус. Этот переход виден в рабочем плане без перезагрузки и не оставляет таймер на завершённой задаче.

Если завершено внешнее предложение, атомарно принять его как локальную задачу и завершить, сохранив ключ источника. Следующее обновление не предлагает его заново.

«Сделано другим человеком» — пользовательская запись об исходе, а не назначение пользователю системы или автоматическая проверка внешнего исполнителя. Не создавать обещание многопользовательского доступа. При неизвестном исполнителе не приписывать работу владельцу Spotter.

После быстрого завершения показать доступное «Отменить». Повторное открытие восстанавливает ту же задачу, прежний приоритет и необходимость разбора. Если приоритета нет, вернуть в неразобранное; если разбор завершён и приоритет есть — в соответствующий квадрант. Включение в уже закрытый план не восстанавливать автоматически.

Для задач с незавершёнными подзадачами запросить явное решение, не отмечать их выполненными молча. Для регулярных задач соблюдать правило единственного открытого выполнения и обработку конфликтов из ТЗ рабочего дня.

## 7. Связь с дневным планом и статистикой

Добавление в план устанавливает связь с задачей, а не переносит или копирует её в другое хранилище. В матрице остаётся отметка «В плане» и дата при необходимости. Удаление из плана не удаляет задачу и её приоритет.

При добавлении показать целевую дату и предложить выделяемое время. Перегрузка и неизвестные оценки выводятся явно. Планирование задач прямо из карточки не требует предварительного назначения приоритета; задача может сохранять признак необходимости разбора. Основной рекомендуемый сценарий остаётся «Неразобранное → матрица → план».

Статистика различает запланированные и внеплановые завершения. Выполненное другим человеком учитывается как закрытое обязательство, но не как личное время фокуса. Повторное открытие корректирует актуальные показатели без удаления истории и двойного подсчёта. Исторические снимки планов не переписываются; правила расчёта за прошлые периоды определяются ТЗ статистики, а не локальным счётчиком Inbox.

## 8. Модель и серверные гарантии

Использовать общую Task и общие команды с рабочей страницей. Нужны отдельные признаки потребности в разборе, происхождения, важности/срочности, завершения и членства в плане. Не сводить их к одному взаимоисключающему полю status.

Продолжить работу с существующим API workspace и оптимистическими версиями. Команды принятия предложения, классификации, завершения, восстановления и добавления в план валидируются на сервере. Конкурентная запись возвращает конфликт и не перезаписывает изменения другой вкладки. Повторная доставка команды не создаёт дубликатов.

Завершение включает запись события, обновление состояния и сохранение ключа дедупликации одной атомарной операцией. Ошибка хранения не должна убирать строку из интерфейса как будто сохранение успешно. Локальные пользовательские решения не затираются обновлением источников или модельными выжимками.

Сохранить локальный режим сервера, существующие проверки Origin и защитного заголовка. В новом UI не обещать чтение не подключённых источников. Данные карточки и комментарии не передавать модели без отдельно определённого контракта.

## 9. Миграция

Перед изменением схемы сделать резервную копию. Существующим задачам без приоритета присвоить неопределённые значения осей; не назначать автоматически квадрант «Не важно, не срочно». Сохранить прежние ID, статусы, проекты, даты, оценки, ключи источников и пропущенные предложения.

Не выводить завершённые задачи в активный Inbox при миграции. Признак повторного разбора не должен сбрасывать начатую работу. Согласовать миграцию с общей схемой рабочего дня, не создавать независимые несовместимые модели задач.

## 10. Соответствие демонстрации и целевой реализации

В образце реализованы компактные строки, модальность основных полей, отдельное меню, классификация/повторный разбор, локальное включение в сегодняшний план, завершение и повторное открытие. Прямое завершение сохраняет связь с существующим планом; активная выборка скрывает завершённую задачу, не удаляя принадлежность.

Только будущая реализация: полный общий редактор со всеми полями и выбором ветки проекта; подзадачи/повторения и проверки их завершения; выбор даты и дневного объёма; единое хранилище с рабочей страницей и её таймером; реальные источники, дедупликация, серверная история и конфликты. Сегодняшний план в демонстрации — локальный флаг без настоящих снимков. Ни сохранение макета, ни успешный UI-тест не подтверждают эти гарантии.

Сокращение полей демонстрации не сокращает функциональные критерии приёмки ниже.

## 11. Критерии приёмки

1. Запись одной строкой создаётся без проекта, оценки и приоритета и появляется в неразобранном.
2. Новое внешнее предложение имеет понятный источник; повторное обновление не дублирует принятую, пропущенную или завершённую запись с тем же ключом.
3. Каждый квадрант задаёт обе оси, а неопределённое значение не считается «нет».
4. Перетаскивание и меню дают одинаковый результат; изменение приоритета не меняет ID и не удаляет план.
5. При 50 задачах интерфейс сохраняет однострочную плотность, счётчики точны, все строки доступны; длинные названия можно прочитать полностью.
6. Название открывает модальную карточку; простая задача не требует заполнения всех полей. Используется общий редактор из ТЗ карточки; в дереве проектов сохраняется отдельный жест двойного клика.
7. Любая локальная задача завершается прямо из Inbox без плана и таймера, в том числе без назначенного приоритета.
8. Завершение внешнего предложения одновременно принимает его и сохраняет дедупликацию; исходное приложение не изменяется.
9. Отмена и повторное открытие сохраняют идентичность и приоритет, не удваивают статистику и не создают план задним числом.
10. Завершение без измерения времени не добавляет нулевую/выдуманную сессию; исполнение другим человеком не увеличивает личный фокус.
11. Возврат из плана сохраняет режим фоновой работы/ожидания, подзадачи и прежние приоритеты, но позволяет повторно разобрать задачу.
12. Потеря доступа к одному источнику, ошибка записи и конфликт вкладок не приводят к потере пользовательских решений.
13. Завершение из меню останавливает активный таймер той же задачи; отмена черновика карточки не завершает задачу и не меняет таймер.
14. Два разных экземпляра регулярного календарного события не склеиваются; повторное получение того же экземпляра не создаёт дубль.
15. Создание из выбранной ветки проектов задаёт проект, но не приоритет; снятое выделение создаёт запись без проекта.
16. Клавиатура и сенсорный экран позволяют выполнить действия без перетаскивания, модальное окно корректно управляет фокусом.

## 12. Порядок реализации и проверки

Сначала согласовать общую модель с ТЗ рабочего дня; затем реализовать миграцию, команды принятия/приоритизации/прямого завершения и связь с планом. После этого — компактные списки, матрицу и доступное управление. Подключить общий редактор по уже подготовленному ТЗ карточки и общую историю комментариев.

Тесты должны проверять реальное поведение: дедупликацию после завершения, повторный разбор без потери состояния, завершение без плана, повторное открытие, конкурентные изменения и миграцию. Отдельно проверить браузером плотность, переносы, длинные названия, модальное окно, клавиатуру и мобильную ширину.

Использовать существующие проверки Go и frontend из README. Проверки на демонстрационных данных не подтверждают реальное подключение Apple-приложений. После реализации обновить README и API-документацию.

Отметка включения в план выводится для выбранной даты из сохранённых PlanItem. Черновое добавление в карточке или подборе плана не создаёт эту отметку в других разделах до успешного сохранения. Несколько дат не сводятся к одному глобальному булевому inPlan.
