# Personal Spotter: общий каркас технического задания

## Название и слоган

- Официальное название продукта: **Personal Spotter**.
- Утверждённый слоган: **Spotter - личное рабочее пространство.**
- В документации, заголовках и пользовательских обозначениях продукта используется полное название **Personal Spotter**. В слогане сохраняется **Spotter**; написание, дефис и конечная точка приведены выше в утверждённом виде.
- Технические идентификаторы, пути, команды, имена образов и API-заголовки сохраняют существующее написание (`spotter`, `X-Spotter-Request` и другие).


Дата: 1 октября 2026 года. Статус: проверенный проект требований, не акт готовности реализации. Пользователь согласовал интерфейс по частям; перечисленные ниже `proposal` требуют отдельного решения. Они не становятся обязательными вследствие наличия в демонстрации.

Связанные спецификации реализации: [модель данных](data-model-spec.md) и [API](api-spec.md). Модель данных имеет приоритет над существующей моделью Go при расхождениях; неутверждённые решения R1–R13 остаются явно выделенными. Оба документа описывают целевой контракт, а не уже реализованные возможности.

## 1. Объём и владельцы контрактов

Общая оболочка, маршруты, вход, сессии и доступ к данным описаны в [архитектуре единого интерфейса](interface-spec.md). Решения U1–U7 в ней имеют статус proposal; наличие документа не означает реализацию авторизации.

| [Inbox](inbox-spec.md) | Предложения источников, принятие, разбор, матрица, завершение вне плана |
| [Карточка](task-card-spec.md) | Один редактор, черновик, поля, подзадачи, комментарии |
| [Календарь](calendar-spec.md) | Даты, рабочие блоки и внешние встречи |
| [Планирование](planning-spec.md) | Диаграмма Ганта, календарные интервалы и дедлайны |
| [Проекты](projects-spec.md) | Иерархия, принадлежность, перенос, текущие сводки |
| [Статистика](statistics-spec.md) | История, границы расчёта, время, результаты, проекты |
| [Моё состояние](wellbeing-spec.md) | Дневник, измерения, подтверждения, три кольца |

Это восемь представлений общей модели, а не восемь приложений. Макеты независимы и не доказывают сквозную синхронизацию. Общая карточка реализуется одним компонентом с одним набором команд; копия редактора внутри макета проектов и сокращённый редактор Inbox не являются архитектурным образцом для копирования.

Существующий Go/HTML/CSS/JS стек и локальный JSON остаются исходной точкой. Проверено в текущем `internal/workspace/workspace.go`: строковый Project, MITDate/MainDate, версии и жёсткие лимиты; новой полноценной истории здесь пока нет. Макеты нельзя подключить к старой модели одной заменой HTML.

## 2. Единые сущности и инварианты

| Сущность | Назначение и инвариант |
|---|---|
| SourceProposal | Запись источника до принятия, ключ дедупликации, контекст и состояние пропуска; не считать её личным обязательством |
| Task / TaskOccurrence | Исполняемая единица. Разовая задача имеет стабильный ID; регулярное выполнение — собственный ID плюс ссылку на правило. Во всех представлениях используется одна и та же исполняемая единица |
| RecurrenceRule | Расписание и шаблон будущих выполнений; не равно текущему выполнению и не является отдельным завершённым результатом |
| Subtask | Один уровень этапов внутри исполняемой единицы; не отдельный результат статистики |
| Project | ID, название, parentId; дерево без циклов, задача имеет не более одного projectId |
| TaskEvent | Событие изменения, время, версия и идентификатор операции; завершение фиксирует исполнителя, сложность и проект на тот момент |
| DayPlan / PlanItem | Дата, пояс, версия и сохранённый выбор конкретных выполнений с дневным объёмом; глобального inPlan на все даты нет |
| DaySnapshot | Неизменяемое состояние версии плана на границе фиксации; ссылка на живую задачу не заменяет снимок её полей |
| FocusSession / TimeEntry | Измеренные активные интервалы и ручное время различимы; оценки будущей работы не являются временем факта |
| DayWellbeingRecord / Measurement | Дата и сохранённый пояс дневника, отдельные измерения с источником/единицей/временем и подтверждениями |

Допустима эквивалентная физическая схема. Требование — однозначная идентичность и связи. Шаблон регулярного дела не имеет одновременно второго жизненного цикла наряду с выполнением; в статистику поступают только выполнения. У правила не более одного открытого выполнения, включая гонки расписания и повторное открытие старого.

Выполнение имеет независимые измерения:

- lifecycle: не начата / в процессе / ожидание / готово;
- workMode только для «в процессе»: активная работа / пауза / фон;
- focus: единственная текущая ссылка, отдельно от состояния и таймера;
- triage: необходимость разбора отдельно от обеих трёхзначных осей приоритета;
- projectId, контекст места, сложность, расписание и plan membership — самостоятельные свойства.

Одна фокусная задача не означает только одну начатую задачу. Смена приоритета не включает задачу в план. Возврат на разбор не стирает приоритет. Перенос между проектами не запускает работу. Неизвестное время, дата, показатель или история не заменяются нулём.

## 3. Команды и общая согласованность

Все разделы используют одинаковые серверные операции создания, принятия, изменения, завершения, повторного открытия и переноса. Операции имеют версию исходных данных и ключ идемпотентности. Конфликт сохраняет черновик; повтор запроса не создаёт второй комментарий, выполнение, снимок или измерение.

Карточка редактирует изолированный черновик. Смена статуса, комментарии, планирование и подзадачи применяются атомарно после сохранения. Быстрые действия вне редактора — самостоятельные команды с теми же проверками. После ответа обновляются все представления, а не только исходная строка.

Переход из фокуса в фон/ожидание/паузу/готово сохраняет активный интервал и снимает фокус атомарно. Причина и контрольная дата старого ожидания остаются историей, но прекращают создавать текущие предупреждения.

Фиксация плана использует один момент времени: закрывает интервал, сохраняет снимок состояний до переключения, затем обновляет актуальный фокус/паузу и возвращает незавершённое на разбор. Все записи одной операции коммитятся вместе. Подбор следующего плана — восстановимый черновик до отдельного сохранения; он не участвует в бюджете, отметках «в плане», переносах и статистике. Неудача сохранения не оставляет частично закрытый день.

Дедлайн только датой сравнивается с исключённой границей следующих суток в соответствующем поясе, а не с выдуманной полуночью начала даты. Назначенное выполнение, дедлайн и появление в Inbox независимы. DST и неоднозначное локальное время требуют явного контракта до выпуска расписаний (решение R12).

## 4. История, время и метрики

Хранить абсолютные временные отметки событий, исходный пояс и датированные планы/дневники. Изменение настроек пояса не переписывает исходные события и даты. Отчёт обязательно возвращает начало, конец, asOf, пояс, полноту истории и версию формулы. Две метрики с разными границами не публикуются как одно неподписанное число.

Сложность по умолчанию средняя только для текущих/новых задач. Завершение фиксирует категорию на тот момент; обычное последующее редактирование не меняет исторический факт. Для старого завершения без категории история неизвестна, миграционный дефолт не восстанавливает её задним числом. Коррекция истории, если разрешена, оформляется отдельным событием, не заменой исходной записи.

Перенос задачи сохраняет исторические ссылки на проект. Текущее дерево показывает текущую принадлежность; исторические отчёты должны применять согласованную R3 политику ко всем уровням. Родитель и дети не складываются повторно в общий итог. Переименование не меняет ID. Добавление, завершение, остаток и время — разные показатели, они не образуют баланс без переносов и повторных открытий.

Время фокуса, число выполненных обязательств и личная активность различаются. Чужое выполнение закрывает обязательство, но не увеличивает кольцо личной умственной активности. Подпункты не увеличивают число результатов. Повторное открытие не удаляет реальные трудозатраты.

## 5. Реестр решений до соответствующего этапа

Все рекомендации ниже имеют статус **proposal**. Без выбора реализуются сохранение исходных данных и согласованные независимые операции; спорный агрегат не выдаётся за утверждённый.

| ID | Выбор | Рекомендация proposal / блокируемый этап |
|---|---|---|
| R1 | Исторический день против пересчёта на конец месяца | Сохранить две явно подписанные границы: дневник на конец дня, месячный график из единого набора на конец месяца. Альтернатива — единый актуальный срез для обоих. Блокирует итоговые агрегаты/кольцо задач |
| R2 | Главный результат меняется в течение дня | Один итог по последнему сохранённому выбору на конец даты, текущий день предварительный; отдельно фиксировать факт закрытия плана. Альтернатива — первый выбор или явное окончательное подтверждение. Блокирует процент успешных дней |
| R3 | Проект активной сессии и историческая иерархия | Делить интервалы на момент переноса; хранить историю parentId и показывать дерево на границу отчёта со стабильными ID. Альтернатива — проект всей сессии и текущее дерево с явной подписью. Блокирует проектную историческую агрегацию |
| R4 | Старые Ready15, WIP3, MIT3, weekly5 против нового плана и целей 3/5/7 | Один фокус сохранить; старые количественные пределы сделать явными настройками/предупреждениями после решения. Альтернатива — сохранить жёсткие пределы; тогда цель 7 задач достижима вне плана/несколькими версиями, но не семью карточками одновременно. Блокирует снятие серверных лимитов |
| R5 | Несколько будущих планов, включение одного выполнения в несколько дат | Разрешать будущие сохранённые планы и отдельные PlanItem дневного объёма; одна активная рабочая версия в выбранной дате. Альтернатива — только один действующий день. Блокирует полноценное многодневное планирование |
| R6 | Перенос многодневного дела против невыполненного дневного объёма | При фиксации отмечать исполнение выделенного объёма отдельно от завершения задачи. Пока нет отметки, показывать нейтральное продолжение. Альтернатива — вообще не оценивать срыв объёма. Блокирует наблюдения о переносах |
| R7 | 7 часов в кольце против существующего SleepTarget | Сохранить прежнюю настройку и отдельный версионируемый ориентир кольца 7 часов с ясной подписью. Альтернатива — единая персональная цель после явного согласия. Блокирует миграцию настройки сна |
| R8 | Смешанная сложность и эмоциональная шкала | Оставить показанный max альтернатив и предложенную шкалу худшего эмоционального компонента; альтернатива — взвешенная сумма и иная шкала. Блокирует окончательные формулы wellbeing, не его хранение |
| R9 | Самостоятельный Pomodoro, длинный перерыв | Первая версия с выбранной задачей, 20 минут длинный перерыв с настройкой; альтернатива — анонимные сессии и другая длительность. Привязку сессии к плану нельзя делать безусловной, если будет разрешён запуск вне плана |
| R10 | Повторение: короткий месяц, текущий экземпляр/будущие | Последний день короткого месяца; правка текущего выполнения не правит шаблон без явного выбора. При конфликте повторного открытия со следующим выполнением нужен экран выбора, не молчаливое удаление. Блокирует расписания |
| R11 | Исправление истории, комментарии, размер полей, конфликт дедлайна | Добавляемые корректирующие события; комментарии первой версии только добавляются; явные единые лимиты полей; конфликт срока предупреждает, а технически неверный интервал блокируется. Альтернатива — блокировать и конфликт дедлайна, как в demo. Блокирует финальную серверную валидацию |
| R12 | Пояса планов/дневника против пояса отчёта; DST | Сохранять date+IANA у плана/дневника, отчёт по умолчанию использует их исходный календарь; альтернативный пояс явно выбран. Для несуществующего времени предложить ближайшее допустимое, для повторённого запросить вариант. Блокирует расписания и смешанные исторические отчёты |
| R13 | Одинаковые имена соседних проектов и предел глубины | Запрет одинаковых соседних имён с понятной ошибкой, минимум3 уровня и явный технический предел. Альтернатива — разрешить с дополнительным различителем. Блокирует финальные ограничения дерева |

## 6. Порядок разработки

1. Утвердить модель ID, версии, события, неизвестные значения и минимальный контракт дат; подготовить резервное копирование и миграцию без выдуманной истории.
2. Реализовать общие команды и единую карточку с черновиком, подзадачами, сложностью и переносом. Подключить Inbox и дерево к одному хранилищу.
3. Внедрить состояния/фокус и надёжный учёт сессий. Затем планы, дневные объёмы, фиксацию, восстановление и повторения после решений R4–R6/R9/R10/R12.
4. Внедрить локальный дневник и измерения, подтверждения и кольца; агрегат задач подключить после R1/R8 и общей истории.
5. Реализовать статистику по согласованным R1–R3/R6/R12 формулам, текущие/пустые/ошибочные периоды, детализацию исходных фактов.
6. Выполнить сквозную приёмку, интеграции проверять отдельно на доступных реальных источниках. Полный HealthKit, системные уведомления, корреляционный анализ и двусторонняя синхронизация не обещаются данным комплектом.

## 7. Сквозная приёмка

- В проекте создать задачу → увидеть тот же ID в Inbox → классифицировать → включить в план → открыть одной карточкой → завершить → увидеть один результат. Повторить с завершением вне плана.
- Приостановить, отправить в фон/ожидание, сменить фокус, закрыть план; проверить сохранность этапов/причин, отсутствие фиктивного времени, снятие устаревших проверок.
- Сохранить два черновика в двух вкладках: одна версия побеждает, другая получает конфликт без потери текста. Повтор запроса после потери ответа идемпотентен.
- Завершить 2-го, открыть 3-го, завершить 5-го; проверить единственность результата по выбранному контракту и объяснимость дневника/месяца.
- Перенести задачу во время сессии, переименовать проект, раскрыть иерархию отчёта: сохранена история, суммы не дублируют потомков.
- Создать регулярное дело, пропустить несколько периодов, перезапустить приложение, выполнить и повторно открыть при наличии следующего: не возникает двух открытых выполнений.
- Пересечь полночь, смену месяца и DST; сменить настройки пояса; ручные записи и снимки не перемещаются молча.
- Миграция: неизвестная трудоёмкость и историческая сложность не превращаются в установленный ноль/среднюю; старая резервная копия пригодна для отката, повтор миграции не дублирует данные.
- Браузер: общий modal, клавиатура/касание, 320 px, настоящие pointer/drag события в целевом контейнере, восстановление после сна и обновления. Тесты прямого фрагмента не заменяют эту приёмку.

Оценка готовности: достаточно для согласования архитектуры, независимых базовых команд и миграционных тестов. Недостаточно для бесспорного выпуска всех вычисляемых показателей и расписаний без решений реестра. Отчёты проверки находятся в [индексе](reviews/README.md).
