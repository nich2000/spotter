# Техническое задание на статистику Spotter

Дата: 1 октября 2026 года. Статус: проект ТЗ, макет предварительно одобрен.

Раздел отвечает на вопросы: что завершено, куда ушло личное время и продвигаются ли проекты. Он показывает результаты и затраты раздельно, без выдуманного универсального балла продуктивности.

Образец: [дашборд статистики](mockups/statistics.html). [Редактируемый исходник](mockups/statistics.fragment.html) обновлён по результатам проверки. Все числа, проекты и наблюдения в нём демонстрационные. Генерация примеров не является алгоритмом расчёта реальной статистики.

Связанные контракты: [рабочий день](workday-spec.md), [Inbox](inbox-spec.md), [карточка](task-card-spec.md), [проекты](projects-spec.md).

Общий контракт сущностей, связей и открытых решений: [каркас проекта](project-spec.md). Он уточняет межраздельные инварианты; решения с отметкой `proposal` не становятся утверждёнными требованиями.

## 1. Структура интерфейса

Сохранить общую верхнюю навигацию и выбор календарного месяца. По умолчанию выбран текущий месяц, доступные предыдущие месяцы берутся из истории. Для незавершённого месяца показывать границу фактически прошедшего периода, будущие дни не считать нулевой продуктивностью.

Последовательность блоков:

1. Завершённые задачи, измеренный фокус, дни с главным результатом, начатые незавершённые задачи.
2. Два графика по дням с общей шкалой дат: время и завершения.
3. Движение по проектам с раскрытием вложенности.
4. Выполнение дневных планов и повторные переносы.
5. Несколько проверяемых наблюдений по данным.

Выбор дня раскрывает фактические задачи и сессии за этот день. Нажатие на задачу открывает общий редактор доступным способом. В интерфейсе различать выбранный период, время обновления и состояние загрузки.

## 2. Источники и полнота данных

Использовать сохранённые задачи/выполнения, события переходов, серверные сессии фокуса, ручные записи времени, версии планов и снимки. Существующего текущего состояния задач недостаточно для достоверной ретроспективы.

Не восстанавливать выдуманное время по оценке трудоёмкости, updatedAt или числу завершённых задач. Не создавать фиктивную историю при миграции. Старые задачи без даты завершения показывать как данные с неизвестной датой, не включать произвольно в текущий месяц.

Отсутствие сессий означает «время не записывалось», а не «пользователь не работал». Ошибка загрузки не равна пустому месяцу. Указывать начало доступной истории и частичное покрытие при необходимости.

## 3. Периоды и временные границы

Календарные сутки и месяцы определяются часовым поясом настроек пользователя. Интервалы задаются как включённое начало и исключённый конец. Сессия, пересекающая полночь или границу месяца, делится по фактическому времени внутри каждого периода.

Текущий день учитывается по момент последнего обновления. Смена часового пояса не меняет временные отметки событий, но меняет их группировку по календарным дням; это должно быть предсказуемо и показано в настройках. Дата самого плана и его исторический снимок при этом не переписываются. До реализации показателя главного результата согласовать сопоставление исходной даты плана с выбранным часовым поясом отчёта; нельзя молча перегруппировать датированный план как событие с временной отметкой.

Дополнительное сравнение с предыдущим периодом допустимо только при сопоставимых границах: полный месяц с полным месяцем либо одинаковое число прошедших календарных дней. Подписывать базу сравнения. Если в предыдущем месяце меньше дней, ограничить оба сравниваемых интервала одинаковым доступным числом дней и показать границы; текущие неполные сутки не сравнивать с полными без обозначения. При нулевой базе не вычислять процент роста делением на ноль — показать абсолютное изменение. При недостаточной истории показывать отсутствие сравнения, не нулевое значение. В макете сравнительные проценты не реализованы и не обязательны для первой версии.

## 4. Определения показателей

### Завершённые задачи

Единица результата — уникальная разовая задача либо конкретное выполнение регулярного правила. Подпункты не увеличивают число задач. Приоритет и наличие дневного плана не обязательны.

Предлагаемый основной расчёт — завершения, действительные на конец выбранного периода: для прошедшего месяца состояние восстанавливается на его конец, для текущего — на момент расчёта. В числитель входят задачи, чей действительный переход в «Готово» произошёл внутри периода и не был отменён повторным открытием до его конца. Несколько переходов одной задачи внутри периода не дают несколько результатов; учитывается последнее действительное завершение.

Так исторические месяцы отражают состояние на свою границу, а текущая статистика реагирует на исправления. Если задачу открыли в следующем месяце, предыдущий снимок не переписывается; в подробностях показывается последующее открытие. Межмесячные итоговые числа нельзя слепо складывать как число уникальных задач за год: для большего периода выполнять расчёт заново по ID.

Для графика выбранного месяца сначала отобрать действительные завершения на общую границу этого месяца, затем разложить этот набор по датам последнего действительного завершения. Не вычислять каждый столбец независимо по состоянию на конец его суток: иначе дневная сумма расходится с итогом месяца после повторного открытия. Детали дня сохраняют контекст выбранного отчётного периода; отменённые завершения можно показать в истории, но не прибавлять к итоговому столбцу.

Контрольный пример предложенного расчёта: задача завершена 2-го, открыта 3-го и снова завершена 5-го. В месячном отчёте на 6-е число она даёт один результат 5-го, ноль 2-го. В самостоятельном отчёте на конец 2-го она давала один результат; различие объясняется границей расчёта. Это правило остаётся предложением до согласования раздела 10.

Отдельно показывать завершения вне дневного плана. Предлагаемое определение: задача не состояла ни в одной сохранённой версии плана на календарную дату завершения до самого завершения. Задача, бывшая в плане вчера, но не сегодня, считается завершённой вне плана сегодняшнего дня. Этот признак фиксируется при событии, не меняется задним числом при добавлении в план.

Отметку «выполнено другим человеком» показывать отдельно в деталях. Это закрытое обязательство, но не личные трудозатраты.

### Время фокуса

Сумма фактических активных интервалов сессий пользователя внутри периода. Паузы, перерывы, фоновый процесс и ожидание ответа исключаются. Неполный Pomodoro добавляет реальное активное время, но не целый завершённый интервал.

Не допускать двойного учёта одной сессии в разных вкладках, проектах и версиях плана. Неопределённое время после сна/разрыва связи требует уточнения и не выдаётся за доказанный фокус.

Ручная длительность показывается отдельно с признаком приблизительности. На графике допускается суммарный столбец из двух отчётливо подписанных частей только для непересекающихся записей. Если ручной ввод описывает то же время, что и сессия, предложить корректировку/замену, а не суммировать молча. Ручная запись содержит дату работы и признак: дополнительное время либо корректировка конкретной записи/сессии. Если дата или отсутствие пересечения неизвестны, не включать длительность в суммарный столбец и показать её отдельно как требующую уточнения. Оценка будущей трудоёмкости задач не является ручным фактическим временем.

Повторное открытие задачи не удаляет уже потраченное время. Активная сессия учитывается только до общей границы расчёта; один и тот же интервал не добавляется снова при финализации сессии.

### Главный результат дня

Одна календарная дата учитывается один раз независимо от числа версий плана. Знаменатель — дни периода с явно выбранным главным результатом; исключить дни, где план ещё не закрыт и день не завершился, либо показать их отдельно как «в процессе».

Предлагаемое правило первой версии: для завершённых календарных дат учитывать последний явно выбранный главный результат действующей на конец даты версии плана; для текущей даты показывать предварительный итог. Нажатие «Подвести итог и собрать новый план» фиксирует версию плана, но не доказывает, что календарный день завершён. До конца даты последующая версия может изменить предварительный результат. Поздние изменения не должны незаметно переписывать историю: сохранять последовательность замен и возможность посмотреть её. День успешен, если выбранная задача находится в завершённом состоянии на конец даты; завершение с повторным открытием до этой границы не даёт успешный день. Открытие на следующую дату не переписывает исторический снимок; показывать факт последующего открытия в деталях. Для незакрытого прошлого дня использовать состояние на границу дня и пометку «день не подведён».

Повторная сборка плана не создаёт дополнительный успешный день. Не выводить процент, если знаменатель равен нулю; показывать «главный результат не выбирался».

### Начато и не завершено

Количество уникальных задач на конец выбранного периода в работе, на паузе, в фоне или ожидании. Не включать только запланированные/не начатые. Показатель отличается от всех открытых задач в проектной таблице. Это остаток на границу периода, а не сумма ежедневных остатков; такую сумму не сравнивать с количеством уникальных начатых задач. Если ранняя история статусов отсутствует, прошлый остаток неизвестен, а не равен текущему состоянию.

## 5. Графики по дням

Верхний график — часы личной работы с раздельными измеренной и ручной составляющими. Нижний — количество завершений по определению выше. Общая ось дат, самостоятельные подписанные шкалы значений. Шкалы адаптируются к данным, а не ограничиваются демонстрационными шестью часами/задачами.

Выбор дня работает мышью, клавиатурой и касанием. Детали содержат дату, покрытие учёта, время по типам, завершённые задачи, признак внеплановости и связанные проекты. В отличие от макета не подставлять одну общую примерную задачу в разные дни.

Для дней без записей отображать отсутствие измерений. Нулевое число зарегистрированных завершений можно показывать как ноль, не делать из него вывод о качестве дня. Будущие даты и периоды до начала истории различать визуально.

Доступная текстовая/табличная альтернатива должна позволять прочитать точные значения, особенно на телефоне, где столбцы слишком узкие для удобного попадания. Цвет дополняется подписями и легендой.

## 6. Проекты

Колонки: проект, добавлено за период, завершено за период, открыто на конец периода, измеренный фокус. Иерархия раскрывается так же, как в разделе проектов. Предусмотреть «Без проекта».

Родительская сводка включает все вложенные задачи один раз. Не суммировать повторно родительскую строку и её потомков в общих итогах. «Открыто» включает и не начатые задачи, поэтому не равно верхнему показателю начатой работы.

Предлагаемая историческая атрибуция: время относится к проекту, зафиксированному в сессии; добавление — к проекту принятия/создания; завершение — к проекту на момент завершения; остаток — к проекту на конец периода. При переносе задачи во время активной сессии уже прошедшие интервалы сохраняют прежний проект; вариант разделения последующего времени по моменту переноса либо фиксации проекта всей сессии должен быть единым с ТЗ рабочего дня и подтверждён в разделе 10. Последующие переносы не переписывают историю затрат. При раскрытии объяснять эту особенность, если переносы влияют на сравнение.

«Добавлено» означает создание/принятие новой задачи, а не перенос существующей между ветками. Разницу «добавлено минус завершено» нельзя объявлять точным изменением остатка без учёта переносов, повторных открытий и архивирования. Наблюдение должно говорить именно о количестве добавлений и завершений.

Время и завершения привязываются к стабильным ID проекта. Переименование меняет отображаемое название, не создаёт новый проект. Стратегию отображения исторического пути при изменении дерева определить совместно с проектной моделью. До выбора этой стратегии запрещено одновременно агрегировать родителя по историческому пути, а дочерние строки — по текущему. Архивированные проекты с историческими событиями остаются доступны в отчёте. Предложения внешних источников до явного принятия и пропущенные предложения не входят в число добавленных/открытых задач; конкретное новое выполнение регулярного правила входит как отдельная задача, повторное открытие — нет.

## 7. Реалистичность планирования

Показывать главный результат и задачи, неоднократно перенесённые на следующую дату. Возврат в Inbox при закрытии плана сам по себе ещё не перенос на следующий день: событие появляется при фактическом выборе задачи в следующий дневной план. Перенос между версиями одной даты не считается переносом дня. Перенос считается для незавершённой задачи при следующем включении в план другой, более поздней даты; повторная отправка команды не увеличивает счётчик.

Для многодневной задачи запланированное продолжение не считать автоматически неудачным переносом. Нужно различать перенос невыполненного дневного объёма и заранее выбранную работу в несколько дней. При отсутствии таких данных показывать нейтральное «запланирована в нескольких днях», а не утверждать срыв.

Предлагаемый порог внимания — три переноса и более. Список должен раскрывать конкретные даты и задачи. Порог является продуктовым предложением, не оценкой дисциплины пользователя.

## 8. Наблюдения

Все наблюдения относятся к выбранному периоду и используют его границу; текущие сигналы требуют отдельной явной пометки «сейчас». Выводить не более нескольких полезных проверяемых фактов: значительное число добавлений относительно завершений, повторные переносы, начатые задачи без изменений более семи дней, наступившие проверки ожиданий. Каждое наблюдение ведёт к подтверждающим задачам/событиям.

Не считать фоновую задачу с будущей контрольной датой зависшей только из-за отсутствия изменения текста. Учитывать содержательные события, а не техническое обновление источника.

Правила детерминированы и не требуют модели. Не выводить медицинские, психологические оценки или причинные выводы из корреляций. Не формировать общий балл «продуктивность 82%». Три личных ориентира из вкладки состояния остаются отдельным показателем по [её ТЗ](wellbeing-spec.md), а не универсальной оценкой статистики. Историческое дневное кольцо состояния по текущему ТЗ wellbeing рассчитывается на конец выбранного дня, а предложенные столбцы месячной статистики — на конец отчётного месяца. Поэтому при повторном открытии позднее эти числа могут различаться. До реализации нужно явно согласовать: сохранять два подписанных представления с разными границами либо выбрать единую границу для обоих разделов. Одобрение макетов такого решения не содержит; не скрывать расхождение и не менять формулы одного раздела без другого. Число выполненных задач здесь не взвешивается по сложности; сложность нужна для отдельных ориентиров состояния и не должна незаметно менять исторические счётчики. Время работы, число задач и важные результаты не взаимозаменяемы.

## 9. API и согласованность

Предусмотреть чтение статистики за период и часовой пояс, детализацию дня и проекта. Ответ включает границы расчёта, момент обновления, полноту истории, единицы и числители/знаменатели показателей. Графики и карточки получают агрегаты одного согласованного снимка.

Расчёты выполняются над общей историей событий и сессий. Для одного периода суммы дневных значений согласуются с верхними итогами с учётом определённых правил повторного открытия. Округлять только отображение, не исходные длительности.

Агрегаты можно кэшировать с инвалидированием после завершения/повторного открытия, корректировки времени и изменений планов. Ошибка пересчёта не должна показываться как нулевые значения. После изменения задачи через карточку обновлять затронутые показатели.

Доступ сохраняется в существующей локальной модели приложения. Новая внешняя аналитика, отправка личной истории и модельная оценка пользователя не требуются.

## 10. Решения для уточнения перед реализацией

- Подтвердить предложенную семантику исторических завершений на конец периода, единый набор завершений для дневных столбцов месячного отчёта и атрибуцию проектов по времени события.
- Выбрать единое правило для активной сессии при смене проекта и исторической иерархии при переносе ветки.
- Уточнить сопоставление датированных планов с часовым поясом отчёта при его смене.
- Согласовать границы с кольцом активности wellbeing: дневной исторический снимок и актуализированный месячный набор имеют разные результаты после повторного открытия. Это блокирует единую неподписанную метрику «задач за день», но не хранение исходных событий.
- Подтвердить правило выбора итогового главного результата при его смене в течение дня. Не вводить метрику без этого правила.
- Определить формат фиксации невыполненного дневного объёма многодневной задачи, чтобы корректно считать переносы.
- Сравнение с предыдущим месяцем оставить дополнительной функцией; не подставлять неподтверждённые проценты.

Предложенные формулы выше не считать утверждёнными только из-за одобрения визуального макета. При реализации до решения этих вопросов отображать подтверждённые исходные числа/историю, а спорную производную метрику не выдавать за согласованную. Базовые требования из обсуждения: отдельный учёт времени/результатов, сохранение истории, отсутствие дублей и различение неизвестного и нулевого значения.

## 11. Граница соответствия сохранённого макета

Макет демонстрирует два завершённых месяца (август и сентябрь 2026), согласованные суммы завершений/фокуса по дням и корневым проектам, динамический масштаб графиков, выбор дня и раскрытие проектов. Выбор сентября по умолчанию — условие демонстрации, а не замена требования текущего месяца в реальном приложении.

Дневные детали не содержат реальной истории: пример результата подписан как пример. Главный результат, остатки, переносы и часть наблюдений заданы демонстрационными значениями; их присутствие не подтверждает расчёт спорных формул. Подробный список задач, открытие общей карточки, события под наблюдениями, «Без проекта», текущий неполный месяц, пустые/ошибочные состояния и интеграция с общим хранилищем требуют реализации. Обязательные требования выше и ниже сохраняются; не использовать генератор демонстрационных чисел в production.

## 12. Критерии приёмки

1. Месячный фильтр меняет все блоки согласованно; текущий месяц не включает будущие дни как неуспешные.
2. Верхние итоги согласуются с дневной детализацией; повторные версии плана не удваивают результат и время.
3. Сессии через полночь/месяц делятся корректно, паузы и перерывы исключены.
4. Ручные оценки отделены от измеренного времени, пересекающиеся записи не суммируются дважды.
5. Завершение вне плана и исполнение другим человеком отражаются без выдуманных сессий.
6. Повторное открытие и повторное завершение соответствуют правилам периода, история не стирается.
7. В проектных сводках нет двойного учёта потомков; переносы не создают новые задачи и фиктивные трудозатраты.
8. Главный результат имеет явный знаменатель, одна дата учитывается один раз, отсутствие планов не равно 0% успеха.
9. Многодневное продолжение не обозначается срывом без данных о невыполненном дневном объёме.
10. Наблюдение раскрывает проверяемые исходные записи; при недостаточных данных вывод отсутствует или помечен.
11. Пустая история, ошибка запроса и отсутствие измерений имеют разные состояния интерфейса.
12. Контрольный сценарий «завершена 2-го → открыта 3-го → завершена 5-го» даёт один итог и один столбец согласно согласованной границе отчёта.
13. Возврат в Inbox без выбора на новую дату не увеличивает счётчик переносов; версия той же даты не создаёт новый успешный день.
14. Архивированный проект сохраняется в истории; непринятые внешние предложения не увеличивают количество задач.
15. Данные доступны клавиатурой и на мобильном экране, точные значения можно прочитать без попадания в узкий столбец.

## 13. Проверка и реализация

Сначала внедрить надёжную историю состояний, планов и сессий по общим ТЗ, затем определить запросы агрегатов и контрольные наборы данных. Реализовать графики и детализацию, затем проектные сводки, планирование и наблюдения.

Тесты: границы суток/месяцев и часовых поясов, неполные сессии, повторное открытие в том же и следующем месяце, задачи вне плана, ручное время, перенос проекта, иерархические агрегаты, несколько версий плана и пустая история. Отдельно проверять тождества сумм и отсутствие двойного учёта.

Браузерная проверка: разные месяцы, длинные названия проектов, 28–31 день, клавиатура, касание, узкий экран и ошибки загрузки. Выполнить применимые проверки Go/frontend из README. Миграция не выдумывает исторические события; недостаточная история явно обозначается.
