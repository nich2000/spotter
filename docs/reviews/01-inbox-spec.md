# Проверка ТЗ Inbox — этап 1

Проверен и исправлен только `docs/inbox-spec.md`. Код и макеты не изменялись.

## Исправлено

- Удалены устаревшие утверждения, что модальная карточка ещё не спроектирована; добавлены ссылки на общий редактор и связанные ТЗ.
- Разведены быстрое завершение из строки и сохранение завершения в черновике карточки. Отмена редактора не должна выполнять команду завершения.
- Определена атомарная остановка активного таймера и снятие фокуса при завершении из Inbox.
- Уточнена дедупликация: область источника и конкретное повторяющееся событие. Исчезновение исходника не закрывает локальную задачу.
- Явно описано создание из дерева: проект определяется выбранной веткой, новая задача всё равно неразобранная.
- Добавлена сложность задачи по пожеланию пользователя, независимо от времени.
- Зафиксирована разница жестов: одиночное нажатие в Inbox, двойное в проектах. Последнее пожелание пользователя относилось к дереву, не ко всем разделам.
- Исторические показатели делегированы ТЗ статистики, снимки не переписываются.
- Расширены критерии приёмки на эти случаи.

## Открытые вопросы для общей проверки

1. Общий контракт сложности должен присутствовать в карточке, модели задач, статистике и состоянии. Значение по умолчанию — средняя; изменение сложности после завершения требует единого правила исторического учёта.
2. ТЗ статистики предлагает учёт завершений на границу периода, рабочий день говорит об актуальном числе завершённых. Эти представления следует явно различать в комплексном ТЗ.
3. Планирование непосредственно из неразобранного оставлено разрешённым как описанное в существующих документах поведение, основной путь — через матрицу. Это не должно становиться обязательным обходом приоритизации.
4. Нужен единый серверный контракт ответа на повторное открытие регулярного выполнения, когда следующее уже открыто; Inbox ссылается на рабочий день и не вводит собственное слияние.
5. Точная стратегия стабильных ключей для нескольких предложенных действий из одной заметки зависит от сборщика; отсутствие устойчивых ID остаётся явным ограничением, а не обещанием безошибочной дедупликации.

## Проверка

Повторно проверены внутренние ссылки, критерии приёмки и согласование с текущими ТЗ карточки, проектов, рабочего дня и статистики. Макет не изменён; соответствие демонстрации новым обязательным действиям относится к следующим этапам пользователя.
