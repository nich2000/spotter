# Проверка ТЗ статистики — этап 1

Изменён только `docs/statistics-spec.md`. Макеты и код не изменены.

## Исправлено и уточнено

- Дневные столбцы месячного отчёта строятся из одного набора завершений на общую границу месяца, иначе сумма дней расходилась с месячным итогом. Сохранён статус предложенной, ещё не утверждённой формулы.
- Добавлен контрольный пример повторного открытия в рамках месяца и различие самостоятельного дневного отчёта с месячным.
- Версия плана больше не трактуется как завершение календарного дня; метрика главного результата учитывает повторное открытие до границы суток и один итог на дату.
- Остаток начатых задач не суммируется по дням; неизвестная история не подменяется текущим состоянием.
- Возврат в Inbox не считается переносом до выбора задачи на другую дату.
- Разделены ручное фактическое время и будущая трудоёмкость; неизвестные пересечения не попадают молча в общую сумму. Повторное открытие не удаляет фактическое время.
- Уточнены неполные сравнения месяцев, нулевая база, архивированные проекты, непринятые предложения, регулярные выполнения и период наблюдений.
- Появились открытые решения по проекту активной сессии и историческому дереву.

## Блокирующие продуктовые решения для общей проверки

1. **Граница числа завершений.** Предложенная статистика пересчитывает дневные столбцы на границу месяца для согласованной суммы. Wellbeing использует конец конкретного дня для исторического кольца. После повторного открытия позднее результаты различаются. Нужно либо утвердить два явно подписанных представления, либо один контракт границы для обоих. Пользователь не утверждал формулу; нельзя назвать её согласованной. Историю событий можно разрабатывать независимо, единую неподписанную метрику — нет.
2. **Главный результат.** Как выбирать итог при нескольких изменениях в день — пока предложение. Успех требует завершённого состояния на границу дня, а не любого события завершения.
3. **Проект во время сессии.** Нужен выбор: интервалы разделяются по моменту переноса задачи либо вся сессия относится к зафиксированному проекту. После выбора привести рабочий день к тому же контракту.
4. **Историческое дерево.** При переносе ветки нельзя смешивать историческую родительскую агрегацию с текущей дочерней; нужен единый подход и сохранённые данные.
5. **Часовой пояс.** UTC-события перегруппируются, дата плана — самостоятельное поле. Требуется правило сопоставления, без переписывания исторического снимка.
6. **Невыполненный дневной объём.** Для многодневных задач данных об одном только членстве в плане недостаточно для обвинительного «переноса».
